# 9.28代码可优化部分

## 1. 文档目的

本文记录截至 9 月 28 日 CBoard 下位机代码中已经识别、但为了优先完成遥控、
安全、控制分配、CAN 电机和后续 MAVLink 通信而暂缓实施的优化项。

当前阶段应先完成真实硬件闭环和基础功能验收。本文内容作为后续重构清单，
不表示需要立即同时修改全部模块。

## 2. 当前应保留的设计

以下职责划分已经比较清晰，后续重构时应继续保留：

- `SbusInput` 负责协议接收和 `input_rc` 发布。
- `RcUpdate` 负责通道校准、映射和归一化。
- `Failsafe` 只发布故障标志，不转发或修改控制目标。
- `RobotControl` 根据手动输入、Failsafe 状态和参数生成安全目标。
- `ControlAllocator` 只负责控制分配，不判断遥控开关和解锁状态。
- `Command` 负责 SA 上电互锁、解锁状态和手动输出禁止。
- `MixingOutput` 负责公共输出映射、消息超时、有限值检查和物理失能。
- `CanOutput` 负责 CAN 设备和达妙协议，不负责上层控制策略。
- 所有 uORB 数据结构继续由 `msg` 目录中的 `.msg` 文件生成。

## 3. 初始化状态与模块生命周期

### 3.1 当前问题

`RobotRuntime` 直接包含 `RcUpdate`、`SbusInput`、`Failsafe`、`RobotControl`、
`ControlAllocator`、`CanOutput` 和 `Command` 的头文件，并逐个调用
`is_running()`。新增必需模块时需要修改 `RobotRuntime`。

目前的 `is_running()` 只说明任务 ID 有效，不能区分以下状态：

- 线程已经创建，但设备初始化失败。
- 线程仍在运行，但内部周期已经阻塞。
- 驱动线程正常，但外部设备未连接。
- 模块运行正常且数据心跳有效。

初始化完成后还应继续检查必需模块。如果运行中某个任务退出，系统状态应从
`READY` 转换为 `DEGRADED` 或 `FAILED`，而不是永久保持完成状态。

### 3.2 后续优化

后续可增加固定容量、无动态内存的模块注册表，并使用模块描述符自注册。
描述符由各模块在自己的 `.cpp` 中声明，不增加中央模块编号枚举：

```cpp
struct ModuleDescriptor
{
  const char *name;
  bool required;
  ModuleState state;
  bool healthy;
  uint64_t lastHeartbeat;
};
```

描述符可以放入专用链接段，由链接脚本使用 `KEEP()` 保留。这样模块即使没有
成功启动，也能以 `Stopped` 状态出现在检查结果中。`ModuleBase` 统一更新
`Starting`、`Running`、`Failed` 和 `Stopped` 状态。

该优化应放到基础功能和通信链路完成后实施，避免当前阶段同时修改所有模块生命周期。

## 4. 系统就绪与允许解锁应分开

### 4.1 当前问题

当前 `_initializationComplete` 是 `RobotRuntime` 的内部变量，只能通过 NSH
打印查看，上位机无法订阅。`ActuatorArmed.valid` 当前表示遥控和开关输入有效，
但名称不足以说明它与系统就绪、允许解锁之间的关系。

系统初始化完成、遥控器连接、允许解锁和已经解锁是四种不同状态：

```text
system_ready     软件和必需驱动已经正常运行
rc_connected     遥控输入链路有效
ready_to_arm     当前满足新的解锁条件
armed            系统已经解锁
```

### 4.2 后续优化

增加 `msg/SystemStatus.msg`，由 `RobotRuntime` 单独发布：

```text
uint8 STATE_INITIALIZING = 0
uint8 STATE_READY = 1
uint8 STATE_FAILED = 2
uint8 STATE_DEGRADED = 3

uint64 timestamp
uint8 state
uint8 requiredCount
uint8 runningCount
uint8 failedCount
bool ready
```

修改 `ActuatorArmed.msg`，明确区分：

```text
bool readyToArm
bool armed
bool controlInputValid
bool lockdown
```

`Command` 通过订阅状态消息计算 `readyToArm`，不要直接调用 `RobotRuntime`
或遥控驱动对象。RC 丢失时禁止新的解锁，但应继续遵守现有要求：已经解锁的
`armed` 不自动清除，由 `Failsafe` 和 `RobotControl` 执行速度置零、转向保持策略。

## 5. 遥控输入协议解耦

### 5.1 当前问题

遥控连接和断开提示目前位于 `SbusInput`。以后增加 MAVLink 遥控输入或其他串口
协议时，每个输入驱动都会重复实现连接状态和用户提示。

### 5.2 后续优化

增加协议无关的 `msg/RcStatus.msg`：

```text
uint8 SOURCE_UNKNOWN = 0
uint8 SOURCE_SBUS = 1
uint8 SOURCE_MAVLINK = 2

uint64 timestamp
uint64 timestampLastSignal
uint8 source
uint8 channelCount
int16 rssi
bool connected
bool signalLost
bool receiverFailsafe
```

调整后的职责为：

- 输入驱动只负责接收、解析并发布 `input_rc`。
- `RcUpdate` 负责生成协议无关的 `rc_status`、摇杆和开关消息。
- `Failsafe` 订阅 `rc_status` 判断遥控故障。
- `Command` 订阅 `rc_status` 判断能否进行新的解锁。
- 连接和断开提示由协议无关层在状态变化时输出一次。

系统初始化不应等待遥控器连接。允许存在以下合法状态：

```text
system_ready = true
rc_connected = false
ready_to_arm = false
```

## 6. MAVLink 通信层

后续 MAVLink 模块应是传输适配器，不直接操作其他模块对象。

发送方向：

```text
system_status ────────┐
rc_status ────────────┤
actuator_armed ───────┤→ Mavlink → MK32/ROS 2上位机
failsafe_status ──────┤
actuator_status ──────┤
battery_status ───────┘
```

接收方向应发布命令消息：

```text
MAVLink接收器 → VehicleCommand/RobotCommand → Command或对应业务模块
```

不要在 MAVLink 接收器中直接调用 `Command::setOutputInhibited()`、
`CanOutput` 或 `RobotRuntime` 成员函数。

基础状态可映射为：

| 下位机状态 | MAVLink状态 |
| --- | --- |
| 初始化中 | `MAV_STATE_UNINIT` |
| 已就绪、未解锁 | `MAV_STATE_STANDBY` |
| 已解锁运行 | `MAV_STATE_ACTIVE` |
| Failsafe生效 | `MAV_STATE_CRITICAL` |

详细模块、测厚、触碰开关、电推杆和电池信息可以通过自定义 MAVLink dialect
定义消息，不把业务字段塞入 `HEARTBEAT`。

## 7. Failsafe 分层

当前 `Failsafe → FailsafeStatus → RobotControl` 的方向正确。后续可以进一步区分：

- RC 丢失。
- 上位机或数传失联。
- CAN 电机反馈超时。
- 电池欠压。
- 触碰开关或测厚执行机构故障。
- 控制目标发布超时。

基础 Failsafe 仍只发布状态和原因，不生成控制目标。不同机器人构型需要复杂策略时，
可以增加构型策略对象；简单策略继续使用参数配置，避免过早建立大量小类。

建议给 `FailsafeStatus.msg` 增加原因位图和严重级别，但不携带 speed、steering
或执行器数组。

## 8. Command 模块职责和命名

当前 `Command` 实际承担的是安全互锁和解锁状态管理，名称容易与 NSH 命令、
MAVLink 命令混淆。后续可根据功能扩展情况选择：

- 保留 `Command` 名称，但明确其只管理 arming。
- 或在 MAVLink 接入时统一重命名为 `Commander`。

无论是否重命名，都不再增加类似 `CommandRouter` 的中央转发类。模块扩展命令继续由
`ModuleBase<T>` 调用各模块的 `custom_command()`。

## 9. uORB 实现能力

当前轻量 uORB 保存每个 topic 的最新一份数据，适合控制状态和周期目标，但暂不具备
PX4 uORB 的完整能力。后续通信增多时需要评估：

- 多发布者和多实例 topic。
- 消息队列及不能丢失的事件消息。
- 每个订阅者独立的 generation 计数。
- 发布频率统计、丢消息统计和延迟统计。
- 阻塞等待或 `poll` 机制，减少固定周期轮询。

控制目标和状态仍可使用“最新值”语义；参数命令、上位机请求和故障事件可能需要队列，
不能统一采用同一种缓存方式。

## 10. 输出层和执行器扩展

`MixingOutput + OutputInterface + CanOutput` 的结构应保留。后续增加 PWM 时应新增
`PwmOutput`，并同样拥有一个 `MixingOutput`，不要在控制分配器中增加 CAN/PWM 判断。

输出功能参数继续决定物理通道绑定：

```text
Motor1、Motor2、Servo1、Servo2 → CAN/PWM具体通道
```

可继续优化的内容包括：

- 将输出超时和中位保持时间改为参数。
- 区分协议写入成功与电机反馈确认使能。
- 统计每个执行器的反馈时间、错误码和掉线状态。
- 允许一个构型把转向执行器从 CAN 电机切换成 PWM 舵机。
- 将达妙协议参数校验和单位换算集中到协议对象。

## 11. 参数系统

参数父子树当前主要用于组织 C++ 对象和统一更新。后续可以补充：

- 参数元数据：单位、范围、步长、枚举和说明。
- 参数修改后是否立即生效、需要重启模块或需要重启整机的标志。
- Flash 双页切换过程的掉电测试和坏页恢复测试。
- 上位机参数读取、设置、保存和恢复默认值的 MAVLink 服务。
- 参数保存失败原因和剩余空间统计。

16 路 RC 校准参数继续使用句柄数组，不需要为每个通道创建一个独立参数子对象。

## 12. 日志和NSH输出

多个任务直接 `printf()` 会导致 NSH 提示符和异步日志混排。后续可以增加轻量日志接口：

```text
ERROR
WARNING
INFO
DEBUG
```

日志接口应支持：

- 时间戳和模块名称。
- 状态变化时立即输出。
- 周期警告限频。
- MAVLink `STATUSTEXT` 或事件消息转发。
- 编译时关闭调试日志以减少固件尺寸。

当前阶段仍可使用 `printf()`，但应继续避免在 20 ms/100 ms 循环中无条件打印。

## 13. ModuleBase生命周期安全

后续需要重点检查：

- `_taskId` 表示“正在创建”还是“对象已经可用”。
- `wait_until_running()` 超时后新线程迟到创建对象的情况。
- `task_delete()` 强制结束线程时对象析构、文件描述符和互斥锁状态。
- `stop`、`status` 和扩展命令并发访问对象的生命周期。
- 原子变量和互斥锁的职责边界。

优先使用协作式退出。强制删除任务只能作为故障恢复手段，不能假定被删除线程一定已经
释放 CAN、UART、锁和动态对象。

## 14. 内存和实时性

后续应建立可重复的资源基线：

- 每个任务的栈峰值。
- 总堆使用量和最小剩余堆。
- 各任务实际运行频率和最大周期抖动。
- CPU 负载和最长关中断时间。
- CAN、SBUS 和 MAVLink 的最大处理延迟。

可以逐步减少运行期 `new/delete`，将长期对象改成启动期一次分配或静态固定容量存储。
不能只通过缩小任务栈来优化内存，必须先取得真实栈峰值。

## 15. 构建系统与板级移植

应用层代码应继续避免直接包含 STM32 寄存器头文件。更换 F7 或其他板卡时，主要修改：

- 板级目录、defconfig、链接脚本和启动代码。
- UART、CAN、PWM、GPIO 和 Flash 的板级映射。
- 内存布局和参数存储扇区。
- NuttX 驱动配置。

业务模块、消息、控制分配和协议代码应保持可复用。

CMake 迁移应在功能稳定后进行。NuttX 最终仍由其 Make/Kconfig 系统构建，CMake 可以用于
组织项目组件、生成代码和主机测试，但不应在当前硬件联调阶段同时替换全部构建入口。

## 16. 测试完善

当前主机测试主要验证算法、消息链路和源代码结构，不能替代板上测试。后续补充：

1. 上电 SA=OFF、SA=ON、遥控器延迟连接三种启动测试。
2. RC 丢失后速度归零、转向保持及恢复测试。
3. 四个 CAN 电机分别掉线、ID 配错和反馈超时测试。
4. 参数保存过程中断电及双页恢复测试。
5. 控制分配任务、Command、Failsafe 或输出任务异常退出测试。
6. MAVLink 断线重连、重复命令和命令确认测试。
7. 电池 CAN、触碰开关、继电器和测厚仪联调测试。
8. 长时间运行时的 CPU、栈、堆和消息延迟测试。

## 17. 建议实施顺序

### 第一阶段：完成基础功能

- 验收初始化成功和失败提示。
- 验收遥控器延迟连接、SA互锁和RC丢失策略。
- 完成四个电机使能、方向、零点、限幅和反馈测试。
- 完成参数掉电保存测试。

### 第二阶段：增加设备功能

- 电池 CAN 状态。
- 触碰开关输入。
- 继电器和电推杆控制。
- 测厚仪数据链路。

### 第三阶段：增加MAVLink与上位机

- 增加 `system_status` 和 `rc_status`。
- 建立 MAVLink 发送、接收和命令确认链路。
- 接入 MK32 界面和 ROS 2 上位机。

### 第四阶段：统一重构

- 模块描述符自注册和健康心跳。
- 初始化状态、解锁状态和设备健康统一建模。
- uORB 队列、多实例和统计能力。
- 日志、资源统计和板级移植接口。
- 评估 CMake 组织方式和 PWM 输出驱动。

按照这个顺序可以避免在硬件尚未完成验收时大规模修改底层框架，同时保留明确的后续
演进方向。
